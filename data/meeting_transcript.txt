Background and Objectives
───────────────────────────────────────────────────────────────
The AP team receives around 1,200 supplier invoices per month as PDFs and phone
photos. Each invoice is checked by hand against the Purchase Order (PO) and the
Goods Receipt Note (GRN), the "three-way match", then against the AP Invoice
Verification Policy. Officers spend most of their time re-typing invoice data and
searching the policy. Two near-misses in Q3 involved invoices asking for payment to
a new bank account.

The CFO asked for a Proof of Concept (PoC) of an AI assistant built on Microsoft
Foundry that reads invoices, checks them against our data and policy, and
recommends an outcome. A human AP Officer always makes the final decision.

════════════════════════════════════════════════════════════════
Summary of Key Points
════════════════════════════════════════════════════════════════

1. System Name and Goal
───────────────────────────────────────────────────────────────
The meeting agreed to name the app "Contoso AP Verify". Phase 1 goal: help AP
Officers verify one invoice at a time faster and more consistently. The app only
RECOMMENDS (APPROVED / ON HOLD / REJECTED); it never posts, approves or pays.

2. Users and Scale
───────────────────────────────────────────────────────────────
Phase 1 users are 2–3 AP Officers testing with the sample invoices in
data/invoices. No need to design for high volume yet. Focus on correctness and a
clear explanation of every check.

3. Tech Stack and Deployment
───────────────────────────────────────────────────────────────
IT wants one simple, Python-only local app. Build it with Streamlit and Python;
do not add a JavaScript frontend or Node.js backend. Run locally on team machines;
no cloud deployment in this phase. Reuse the Microsoft Foundry Python examples in
python_examples/ for every Foundry call; do not invent new SDK patterns.

4. Feature 1: Invoice Upload and OCR
───────────────────────────────────────────────────────────────
The officer uploads a PDF or image. The app extracts header fields (invoice number,
dates, PO number, vendor name and tax ID, buyer tax ID, bank details, subtotal, VAT,
total) and line items. Use Document Intelligence prebuilt-invoice for PDFs and the
vision model for photos (python_examples/02_ocr_invoice.py). Show the extracted fields in an
editable form so the officer can correct OCR mistakes before verification.

5. Feature 2: Three-Way Match and Controls
───────────────────────────────────────────────────────────────
After OCR, run the deterministic checks in python_examples/verify.py against the AP database:
vendor master, blocked vendor, bank account change, duplicate invoice, PO exists,
unit price tolerance, quantity vs received, subtotal tolerance, VAT 7%, approval
level and withholding tax. Show each check as a row with PASS / HOLD / REJECT, the
policy section, and the detail. Kanya was firm: pass/fail must come from rules, not
from the AI model.

6. Feature 3: Ask the Policy (Vector Search)
───────────────────────────────────────────────────────────────
A chat panel where officers ask questions about the AP Invoice Verification Policy
(data/Contoso_AP_Invoice_Policy.pdf) using File Search (python_examples/03_vector_search.py).
Answers must cite the policy section. If the answer is not in the policy, the bot
must say so and point to ap-policy@contoso.example. When an invoice has
exceptions, automatically ask the policy what to do and show the guidance.

7. Feature 4: Ask the Data (Text2SQL)
───────────────────────────────────────────────────────────────
Officers often ask ad-hoc questions such as "which invoices are on hold?" or "what
did we pay this vendor this year?". The chat should answer these from the AP
database using Text2SQL (python_examples/04_text2sql.py). Always show the generated SQL in a
collapsible block so the answer can be audited. Read-only: SELECT queries only.

8. Feature 5: Web Check (Web IQ)
───────────────────────────────────────────────────────────────
Arthit asked for a way to confirm current Thai tax rules (VAT, withholding tax
rates, filing deadlines) and Bank of Thailand FX rates, because the policy can lag
behind Revenue Department announcements. Use Microsoft Web IQ
(python_examples/05_web_iq.py). Always show source links and prefer official sources
(rd.go.th, bot.or.th). Web results are advisory only and never change a rule result.

9. Routing the Chat
───────────────────────────────────────────────────────────────
One chat box. The app decides whether a question is about the POLICY, the DATA,
or the WEB, and shows a small badge ("Policy", "Data", "Web") on each answer. If
unsure, ask the user a short clarifying question.

10. Chat History
───────────────────────────────────────────────────────────────
Keep the last 5 turns in memory (sliding window). No database for chat history.
The currently loaded invoice and its check results should be available as context
so the officer can ask "why is this on hold?".

11. Out of Scope for Phase 1
───────────────────────────────────────────────────────────────
- Writing to the AP database, approving or paying invoices
- Email integration and supplier notifications
- User login and roles (single local user)
- Thai-language OCR tuning (sample invoices are in English)

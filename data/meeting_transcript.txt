"Contoso AP Verify" | บริษัท คอนโทโซ (ประเทศไทย) จำกัด ฝ่ายการเงิน

เวลา: 14:00 ถึง 15:30 น.
สถานที่: ห้องประชุม 7B / Microsoft Teams

ผู้เข้าร่วมประชุม
- กัญญา วงศ์สุวรรณ ผู้จัดการบัญชีเจ้าหนี้ (ประธาน)
- มาลี ชัยพร เจ้าหน้าที่บัญชีเจ้าหนี้อาวุโส
- ธนพล รุ่งโรจน์ นักพัฒนาระบบ ฝ่าย IT
- พิมพ์ชนก สุขสวัสดิ์ เจ้าหน้าที่ IT / ผู้ดูแลระบบ
- อาทิตย์ บุญมี ผู้เชี่ยวชาญภาษี (เข้าร่วมในหัวข้อภาษี)

หมายเหตุ: บริษัท บุคคล เลขผู้เสียภาษี และบัญชีธนาคารทั้งหมดเป็นข้อมูลสมมติ
ใช้เพื่อฝึกอบรมเท่านั้น ไม่ใช่คำแนะนำด้านภาษีหรือกฎหมาย

ที่มาและวัตถุประสงค์
ทีมบัญชีเจ้าหนี้ (AP) รับใบแจ้งหนี้ประมาณ 1,200 ฉบับต่อเดือน ทั้ง PDF และภาพถ่าย
เจ้าหน้าที่ต้องพิมพ์ข้อมูลใหม่ แล้วเทียบใบสั่งซื้อ (PO) ใบรับสินค้า (GRN)
และใบแจ้งหนี้ หรือ "การตรวจสอบเอกสารสามทาง" พร้อมค้นหานโยบายที่เกี่ยวข้อง
ในไตรมาส 3 มีสองกรณีที่เกือบจ่ายเงินไปยังบัญชีธนาคารใหม่โดยยังไม่ได้ยืนยัน

CFO ขอระบบต้นแบบ (PoC) บน Microsoft Foundry เพื่ออ่านเอกสาร ตรวจข้อมูลกับนโยบาย
และเสนอผลการตรวจสอบ โดยเจ้าหน้าที่ AP ที่เป็นมนุษย์ต้องตัดสินใจขั้นสุดท้ายเสมอ

ข้อสรุปการประชุม

1. ชื่อระบบและเป้าหมาย
ใช้ชื่อ "Contoso AP Verify" ระยะแรกช่วยตรวจใบแจ้งหนี้ครั้งละหนึ่งฉบับให้เร็วและสม่ำเสมอ
ระบบให้เพียงคำแนะนำ APPROVED (ผ่านการตรวจสอบ), ON HOLD (พักรายการ),
หรือ REJECTED (ปฏิเสธ) ไม่บันทึกบัญชี ไม่อนุมัติ และไม่จ่ายเงินจริง

2. ผู้ใช้และขนาดระบบ
เจ้าหน้าที่ AP 2 ถึง 3 คนทดลองกับเอกสารใน data/invoices/
ยังไม่ต้องรองรับงานปริมาณสูง เน้นความถูกต้องและคำอธิบายแต่ละข้อ

3. เทคโนโลยีและการรันระบบ
ธนพลเสนอแยกส่วนแสดงผลออกจากส่วนประมวลผล:
- Frontend: React + Vite ใช้ Node.js 22 LTS ขึ้นไปสำหรับ npm และ dev server
  สร้างใน frontend/ ให้หน้าจอ ปุ่ม และข้อความผู้ใช้เป็นภาษาไทย
- Backend: Python 3.11 ขึ้นไป + FastAPI ใน backend/main.py
  รันจากรากโครงการด้วย python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
- การเรียก OCR, Microsoft Foundry, Vector Search, Text2SQL และ Web IQ
  ต้องอยู่ฝั่ง Python เท่านั้น โดยใช้ python_examples/workshop_api.py และตัวอย่างเดิม
- เก็บ API key ใน .env ฝั่ง Python ห้ามใส่ใน frontend, ตัวแปร VITE_*, หรือส่งไปเบราว์เซอร์
- Frontend เรียก /api/* ผ่าน Vite proxy ไปที่ http://127.0.0.1:8000
  ไม่เพิ่ม Express หรือ Node.js backend สำหรับ AI และไม่ใช้ Streamlit
- รันเฉพาะเครื่องผู้เรียน ไม่มี cloud deployment ในระยะแรก

พิมพ์ชนกย้ำว่า Vite proxy ต้องใช้ได้ใน Codespaces ด้วย
Frontend ใช้พอร์ต 5173 สำหรับ dev server และมีเพียง frontend ที่ต้อง forward port
Backend อยู่ภายในเครื่องเดียวกัน ไม่เปิดพอร์ตสู่สาธารณะ

4. อัปโหลดใบแจ้งหนี้และ OCR
ผู้ใช้เลือก PDF, PNG หรือ JPG ส่งเป็น multipart field ชื่อ file ไปที่ POST /api/extract
Backend บันทึกไฟล์ชั่วคราว ใช้ extract_invoice แล้วลบไฟล์ใน finally แม้ OCR ล้มเหลว
ตรวจนามสกุลและจำกัดไฟล์ไม่เกิน 10 MB
แสดงข้อมูลหัวเอกสารและรายการสินค้าให้แก้ไขได้ก่อนตรวจสอบ
ข้อมูลสำคัญคือเลขที่ใบแจ้งหนี้ วันที่ เลข PO ผู้ขาย เลขผู้เสียภาษีผู้ขายและผู้ซื้อ
บัญชีธนาคาร ยอดก่อนภาษี VAT ยอดรวม และรายการสินค้า
เอกสารตัวอย่างเป็นภาษาไทย วันที่ในใบแจ้งหนี้และฐานข้อมูลใช้ ค.ศ. ในรูป YYYY-MM-DD
ต้องรักษาชื่อและรายละเอียดภาษาไทยตามเอกสาร ไม่แปลกลับเป็นภาษาอังกฤษ

โหมดออฟไลน์สำหรับสาธิต: ให้ผู้ใช้เลือกเอกสารตัวอย่างที่ระบุชื่อแน่นอน
ส่ง JSON {"filename":"INV-TTS-2026-118.pdf"} ไป POST /api/offline-invoice
Backend อ่านเฉพาะชื่อที่มีอยู่ใน data/invoices/ground_truth.json
ไม่รับ path จากผู้ใช้ และไม่เรียก AI ในโหมดนี้

5. การตรวจเอกสารสามทางและมาตรการควบคุม
ส่งข้อมูลที่แก้ไขแล้วเป็น JSON object ของใบแจ้งหนี้ไป POST /api/verify
Backend เปิด sqlite3 จาก data/ap_database.sql ในหน่วยความจำและปิดเมื่อจบคำขอ
ใช้ python_examples/verify.py:verify_invoice ตรวจทะเบียนผู้ขาย ผู้ขายถูกระงับ
การเปลี่ยนบัญชี ใบแจ้งหนี้ซ้ำ PO ราคา จำนวนที่รับ ยอดก่อนภาษี VAT 7%
ระดับผู้อนุมัติ และภาษีหัก ณ ที่จ่าย
แสดงผลแต่ละข้อเป็น PASS / HOLD / REJECT พร้อมเลขข้อนโยบายและรายละเอียด
กัญญาย้ำว่าผลต้องมาจากกฎ Python เท่านั้น ไม่ใช่การตัดสินของโมเดล
ใช้รหัสผลภาษาอังกฤษเดิมใน JSON แต่แสดงป้ายและคำอธิบายภาษาไทยบนหน้าจอ

6. ถามนโยบาย (Vector Search)
ใช้ ask_policy ค้น data/Contoso_AP_Invoice_Policy.pdf ผ่าน File Search
ตอบเป็นภาษาไทยพร้อมอ้างเลขข้อนโยบาย ถ้าไม่มีข้อมูลให้บอกตรง ๆ
และแนะนำ ap-policy@contoso.example ไม่สร้างคำตอบเอง
เมื่อพบข้อยกเว้น ควรให้ปุ่มถามนโยบายว่าต้องดำเนินการต่ออย่างไร

7. ถามข้อมูลภายใน (Text2SQL)
ใช้ ask_data สำหรับคำถาม เช่น "มีใบแจ้งหนี้ใดพักรายการอยู่ เพราะอะไร"
หรือ "ปี 2026 จ่ายเงินให้บริษัท พระรามบริหารทรัพย์สิน จำกัด ไปเท่าไร"
แสดง SQL ที่สร้างในส่วนพับเก็บได้ พร้อมข้อมูลผลลัพธ์และคำตอบภาษาไทย
ใช้ assert_read_only ก่อนรัน SQL ทุกครั้ง อนุญาต SELECT หรือ WITH ... SELECT
เพียงคำสั่งเดียว ห้ามเขียนข้อมูล
ชื่อคอลัมน์ รหัสผู้ขาย รหัสสินค้า สถานะ และวันที่ ISO ใช้รูปเดิม
แต่ชื่อบริษัท แผนก รายละเอียดสินค้า และหมายเหตุเป็นภาษาไทย

8. ตรวจข้อมูลภายนอก (Web IQ)
อาทิตย์ขอให้ตรวจอัตรา VAT ภาษีหัก ณ ที่จ่าย กำหนดยื่นแบบ
และอัตราแลกเปลี่ยนจากแหล่งข้อมูลปัจจุบัน เพราะนโยบายอาจปรับช้ากว่าประกาศ
ใช้ ask_web แสดงคำตอบภาษาไทยและลิงก์แหล่งที่มา เน้น rd.go.th และ bot.or.th
ผลเว็บเป็นข้อมูลประกอบเท่านั้น ห้ามเปลี่ยนผลตรวจจากกฎโดยอัตโนมัติ
บริษัทตัวอย่างเป็นข้อมูลสมมติ จึงไม่คาดหวังผลค้นหาข่าวผู้ขายจริง

9. การเลือกเส้นทางแชต
มีช่องแชตเดียว ใช้ POST /api/chat รับ JSON:
{"question":"คำถามภาษาไทย","history":[],"invoice":null,"verification":null}
ให้ Python ใช้ route_chat แล้วเรียก ask_policy, ask_data หรือ ask_web
คืน {"route":"policy|data|web|out_of_scope|clarify","answer":"...","sql":null,"sources":[]}
เส้นทาง data ต้องคืน SQL จริง เส้นทาง web ต้องคืนแหล่งอ้างอิงจริง
ถ้าไม่เกี่ยวกับ AP ให้ปฏิเสธสุภาพ ถ้าไม่ชัดให้ขอข้อมูลเพิ่ม
ป้ายเส้นทางภาษาไทยบนหน้าจอ: "นโยบาย", "ข้อมูล", "เว็บ"

10. ประวัติแชตและสถานะ
เก็บประวัติ 5 รอบล่าสุด (สูงสุด 10 ข้อความ user/assistant) ใน React memory
ไม่ใช้ localStorage และไม่เพิ่มฐานข้อมูลประวัติ Backend ต้องจำกัดซ้ำก่อนเรียก AI
ส่งใบแจ้งหนี้และผลตรวจปัจจุบันเป็นบริบทด้วย
เพื่อให้ถามต่อได้ว่า "ทำไมใบนี้จึงพักรายการ"
เมื่อสลับใบแจ้งหนี้ ต้องล้างผลตรวจเดิมเพื่อไม่ให้แสดงผลผิดฉบับ

11. การแจ้งข้อผิดพลาดและสิ่งที่อยู่นอกขอบเขต
Frontend ต้องแสดงสถานะกำลังทำงาน ป้องกันการส่งซ้ำ และแสดงข้อความผิดพลาดจาก backend
Backend คืน HTTP error เมื่อการตั้งค่าไม่ครบ ไฟล์ไม่ถูกต้อง หรือบริการ AI ใช้งานไม่ได้
ห้ามส่ง API key หรือ traceback ให้เบราว์เซอร์ ห้ามแทนข้อผิดพลาดด้วยผลสำเร็จปลอม
ไม่รวมการเขียนฐานข้อมูล AP อนุมัติหรือจ่ายเงิน การเชื่อมอีเมล การแจ้งผู้ขาย
ระบบล็อกอิน สิทธิ์ผู้ใช้ และการฝึกโมเดล OCR ภาษาไทยเฉพาะทาง
